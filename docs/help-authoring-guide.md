# CellulosesZ help authoring guide

How to write command help Markdown. Resources live at
`modules/<module>/src/main/resources/cellulosesz/help/<lang>/<category>/<literal>.md` for `en_us`
and
`zh_cn`. The command catalog (name, aliases, usage) is generated from the Kotlin command DSL; the
help prose is hand-written and kept honest by the resource-coverage check. This guide is the voice
contract for that prose.

## 1. What the reader wants

Already knows the command name. Wants to confirm: how to use it, what happens, and what to do when
it fails. Answer those first.

## 2. Section order (use only the sections that carry real information)

1. Title + short summary: `# /command`, one or two sentences naming the purpose and object.
2. Usage: generated by `CommandUsage.patterns()` from the DSL. Only explain subcommands/arguments in
   prose when it helps; never hand-copy the whole syntax tree.
3. Behavior: who can use it, what/who it affects, what happens. Only what the player must know.
4. Examples: real, executable, each with `/`, one per line.
5. Limits and cautions: state when a default comes from config and can change. Call out deletes,
   clearing, bans, item drops and persisted records.
6. If it doesn't work: the real, main failure conditions, with a fix only when one exists.
7. Related commands: only genuinely related ones.

Not every document needs every section. A simple workstation command needs a sentence, an example
and one real limit.

## 3. Keep implementation out of player help

No Kotlin, threads, JDBC, Brigadier, event ordering, JSON/SQL, or internal reservation states. When
an internal detail changes what the player experiences, write the outcome instead:

| Internal description                                     | What the player needs                                                                  |
|----------------------------------------------------------|----------------------------------------------------------------------------------------|
| "read on the server thread"                              | "saves the location where you ran the command."                                        |
| "reserves before delivering, so a crash can't duplicate" | "if delivery is interrupted the claim may already be recorded; ask an admin to check." |
| "vanilla account ban list is the source of truth"        | "banned players can't join; use `/unban` to lift it."                                  |
| "session-only, not persisted"                            | "monitoring/vanish turns off again after you reconnect."                               |
| "vanilla only enforces IPv4 fully"                       | "IP bans mainly cover IPv4 addresses; check the address before using it."              |

## 4. Examples must be real

- Each example on its own list item, with a leading `/`. Do not put adjacent backticked lines in one
  paragraph (they merge into one line): use a list.
- No non-existent subcommands, unparseable arguments, invalid dimension IDs, unclosed quotes or
  wrong permission claims. Fix examples such as `sethome base` missing the `/`.
- Links like `[see homes](/home)` become a click that *suggests* the command; they do not run it.
  `https://` links open a page. No images or raw HTML.

Write these as "default", not as fixed limits, and only where they matter to the command.

## 6. Length and rendering

- Help is sent as one whole document (ADR 0012 has no pagination). Check the real chat output.
- Simple command: ~15-22 lines is often enough. Multi-argument or high-impact commands may be
  longer; remove blank-line noise and duplicated usage before adding content.
- Markdown supports headings, paragraphs, bold, italic, inline code, fenced code, ordered/bullet
  lists, block quotes, `[!TIP]`/`[!NOTE]`/`[!WARNING]` callouts, thematic breaks and links. Tables
  are not rendered; don't use complex tables.
- The help body does not use the short-message `[[...]]` / `{0}` template syntax.
- If a document grows past a readable screen, update ADR 0012 before changing to per-subcommand
  docs; don't silently add pagination.
